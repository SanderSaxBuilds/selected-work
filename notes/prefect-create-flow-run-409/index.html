Prefect's create_flow_run answered 409, its OpenAPI document said 422

Alexandr Khrustalev, November 2026

$ curl -i -X POST $API/deployments/$DEP_ID/create_flow_run
HTTP/1.1 409 Conflict
{"detail":"Error creating flow run: Validation failed for field
 'count'. Failure reason: 'not-a-number' is not of type 'integer'"}

$ documented responses
['200', '422']

I wrote a TypeScript client for Prefect's REST API from its OpenAPI document, then ran it against a real prefect server start on version 3.9.2. Most of the document matched the server. One of the most used calls did not.

What the server returns

A deployment can set enforce_parameter_schema to true, so every run it starts has to match the deployment's parameter schema. Send a string where the schema wants an integer, or leave out a required parameter, and POST /deployments/{id}/create_flow_run answers 409 Conflict with a detail string that names the field.

The OpenAPI document listed 200 and 422 for this operation. A request that passes creates the run and comes back as 201, which was not listed either. So the two answers a caller sees most often, a new run and a rejected one, were both missing from the document.

Why a client cares

A client built from the document only knows the responses written in it. Following the document strictly, it has no type for a new run and no shape for the rejection, so the field name in detail never reaches the person who sent the bad parameter. Treating every 2xx as success and every other status as an untyped error works, but it throws away the one message that says what to fix.

A 409 also reads as a state conflict, such as a run that already exists. For a parameter that is the wrong type, a caller would expect the 422 the document promised.

What changed upstream

I reported it as issue 23877 with a script that reproduces it from an empty server. The maintainers kept the 409. It came in with an earlier change, tests depend on it and clients may already check for it, so changing it to 422 would break working code. They documented it instead.

The fix was merged on 19 November. create_flow_run now lists 200 for an existing run returned by its idempotency key, 201 for a new run, 400 when parameters cannot be hydrated or a work queue is given without a work pool, 404 for an unknown deployment and 409 for a schema mismatch. PATCH /deployments/{id} got the same error codes, and two new tests read /openapi.json so the list cannot quietly fall behind again.

What a client should do now

Handle 409 from create_flow_run as a validation error and show the detail string, since it names the field. Accept both 200 and 201 as success, and keep the idempotency key if you retry, so a retry returns the first run instead of starting a second one.

Read 422 bodies with care. Prefect's server sends exception_message and exception_detail, while the document describes the usual FastAPI detail array. That one is still open, so a client should accept both shapes.

The wider habit is cheap. Run every error path of a generated client against a live server once, and compare the codes it gets with the codes the document lists. It took one script here, and it found two codes the document missed.
