Gumroad retries a failed Ping, unless n8n already said yes

Alexandr Khrustalev, November 2026

# gumroad: app/sidekiq/post_to_individual_ping_endpoint_worker.rb
ERROR_CODES_TO_RETRY = [499, 500, 502, 503, 504]
BACKOFF_STRATEGY = [60, 180, 600, 3600]
REQUEST_TIMEOUT_SECONDS = 5

A seller on the n8n jobs board wrote that their Gumroad to Airtable workflow looked like it worked but did not record sales. I built a replacement for that job, and the cause is worth writing down, because the default settings on both sides lose a sale without showing an error anywhere a seller would look.

What Gumroad does when your endpoint fails

Gumroad's app is open source, so its Ping delivery can be read instead of guessed. The worker posts the sale as a form, waits up to 5 seconds and looks at the answer. A 2xx ends it. A 499, 500, 502, 503 or 504, a timeout or a refused connection schedules another try. Any other status, such as 404, 401 or 400, ends it with no retry.

The retry check is retry_count < BACKOFF_STRATEGY.length - 1, so a sale gets at most four attempts: right away, then 1 minute, 3 minutes and 10 minutes after each failure. The fourth value, one hour, is never used. Newer versions of the code also record each attempt and its status code, so a seller can see what their endpoint answered.

What n8n answers by default

The Webhook node's Respond option defaults to Immediately. In the node source that is default: 'onReceived'. n8n answers 200 with "Workflow got started" before the next node runs.

If the Airtable write then fails, because of a rate limit, a renamed field or an expired token, Gumroad has already been told the sale arrived. It will not send it again, and the only trace is a failed run in the workflow's Executions tab.

Two ordinary setups end the same way with a 404. The test URL only answers while the editor is listening for a test event, and the production URL is only registered once the workflow is published. Point Gumroad at either one at the wrong moment and the sale is dropped on the first attempt.

The fix

Set Respond to When Last Node Finishes. Gumroad then waits for the Airtable step, and a failed write fails the run, so n8n answers with a server error instead of a 200. That is a status Gumroad retries.

Make the write an upsert keyed on the sale ID. Retries mean one sale can arrive more than once. In my workflow the Airtable request may take up to 15 seconds while Gumroad gives up after 5, so a slow write can land and still be retried. Airtable's update endpoint with performUpsert and fieldsToMergeOn set to sale_id updates the row it already has instead of adding a second one.

PATCH https://api.airtable.com/v0/{base}/{table}
{
  "performUpsert": { "fieldsToMergeOn": ["sale_id"] },
  "records": [{ "fields": { "sale_id": "...", "amount_cents": 725, ... } }]
}

Check the totals every day. Four attempts over about 14 minutes cover a short outage. They do not cover an n8n instance that was down for an hour, a workflow someone unpublished or a table someone renamed. My check pulls sales from the Gumroad Sales API, matches them with Airtable by sale ID and reports missing sales, wrong amounts and duplicate rows. With --fix it adds the missing ones, and its exit code tells a scheduler whether to alert.

Smaller things in the payload

The payload builder answers a few questions that come up when mapping fields.

price is price_cents. A workflow that writes it into a currency field shows a 7.25 USD sale as 725.

test is only sent, as true, when the buyer is the seller. Real sales have no test key at all, so map a missing key to false.

refunded describes the sale at the moment of the Ping. A refund issued later does not reach that row on its own.

Custom checkout fields are copied into the top level of the payload under their own names, after email and price are set. A custom field named email would replace the buyer's address.

If the seller sets a signing secret, Gumroad adds an X-Gumroad-Signature header, an HMAC-SHA256 of the timestamp and the body. Without it, anyone who learns the webhook URL can post a fake sale, so check the header in a Code node or keep the URL path long and random.

The workflow, the daily check and their tests are in gumroad-airtable-sync on GitHub.
